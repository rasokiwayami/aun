# 質問集と面談プランナー

`src/questions.json` は設計提案「ひとつずつ」1.0（2026-10-05）の `04_questions.json` を取り込んだ300問・22カテゴリの質問集です。原案のID、改訂番号、本文、優先度と理由、判断用途、適用条件、追質問、十分条件、感度、非回答選択、更新契機、表示条件、共通方針をそのまま保持しています。本文の改変はありません。原案の状態表示 `proposed; structurally checked; content validity not yet established` も残しています。

原ファイルの SHA-256 は `e80c3e7ef1c51a766aa7618ba9857758453049552246e95197bdbf95df13ef02` です。追加したフィールドは各問の `goal_id`・`topic_ids`・`purposes` と、ファイル全体の `implementation` です。旧版の200問と新IDとの間には意味の一致が保証されないため、自動対応表は設けていません。旧記録を新質問への回答済み情報として自動採用しません。

## 判断を共通化する範囲

`src/question-goals.json` に全300問の対応を明示しています。現在の253 goalは実装時の編集判断です。同じ判断不足を尋ねる近接項目は共通goalを使います。たとえばVAL-001とDEC-001は候補を除外する条件、PRI-001・COM-005・VAL-006・ETH-011は内部判断と外部開示の区別、LIF-002とNOW-010は準備時間です。汎用条件と今回の条件を同一goalにまとめたものもあります。予算を場面ごとに増やさないための保守的な選択であり、回答の意味や適用範囲を同一視するものではありません。

意味上近いが同じ判断ではない項目には共通topicを付けます。拒否はcategoryとsemantic topicの両方にかかり、共通goalの別カテゴリの質問にもsemantic topicを引き継ぎます。この方式は拒否の回避を防ぐため、本人の意図より広い範囲を止める場合があります。再開は本人の明示操作だけで行います。質問選択モデルの `next`・`follow_up`・語句の言い換え・場面変更は再開操作になりません。

## プランナーの契約

`questions.mjs` は読取専用の質問配列、カテゴリ、topic選択肢、最初の18候補、ID・goal検索を公開します。`planner.mjs` は外部通信・保存・時刻読取を行わない純粋関数です。

- `createInquiry()` は面談状態を作ります。
- `eligibleQuestions(options)` と `nextQuestion(options)` は候補配列と先頭の一問（なければ `null`）を返します。
- `recordQuestion(inquiry, id)` は実際に表示を確定した一問につき一回呼びます。通信再試行の重複排除は呼出側のoperation IDが担当します。
- `navigateInquiry` は `skip`・`defer`・`unknown`・`not_applicable`・`refuse`・`stop`・`topic`・`partial`・`sufficient`・`covered`・`continue`・`resume` を扱います。変更前のオブジェクトは更新しません。
- `validateQuestionChoice` はモデルが選んだIDを検証し、真偽値を返します。モデルが渡せる移動種別は `next` と `follow_up` だけです。
- `applyEvidenceCoverage(inquiry, updates, source)` は今回の原文のID・現行revision・文字範囲・完全一致の引用を検査してから、`partial`・`sufficient`・`unknown` の状態だけを更新します。sourceはコミット時に呼出側が読み出した本人の原文です。入力全体を検証してから更新し、不正な項目が一つでもあれば例外にします。拒否・保留・不明・予算切れ・停止を解除せず、権限や知識の本人確認にも変更を加えません。根拠をgoalの `evidence` に保存するため、原文の訂正・削除時には呼出側で派生状態も失効させる必要があります。

一つのgoalには通常、最初の質問と追質問一回の計二回の予算があります。明示の `continue` で最大計三回まで増やせます。同じIDでも別IDでも、`next`というラベルでも、別の話題・scopeを挟んでも合計します。`partial` の状態でのみ継続でき、通常の自動選択は一度表示したIDを再表示しません。同じIDで追質問する際は `follow_up` の検証を通します。追質問の文面は原案の条件を守って調整する必要があります。

`unknown`・保留・適用外・拒否・十分・既存情報で充足の状態は自動で復活しません。日数経過やモデルの「再開」提案による更新はありません。明示の `resume` にquestionIdを指定すると、そのgoalの履歴と対応topicの抑止を解除します。topicを指定した再開ではそのtopicの抑止と該当goalを解除しますが、別のtopicの拒否は残ります。対象を指定しない再開はセッションの停止だけを解除します。

purposeは `self_reflection`・`conversation`・`draft_reply`・`compare`・`learn`・`create`・`plan` に限定します。`plan` は現在条件、生活、活動、資源、比較、目標など計画に関係するカテゴリへ付けています。質問のpurposesは粗い用途フィルタです。`applicableIds` を渡せば、その明示集合を追加の必須条件とします。`coveredGoals` は今回の用途・場面で適用できる根拠から呼出側が作る情報で、質問IDへの回答済みフラグや本人確認とは別です。適用外の過去の知識まで一律に渡さないでください。

自由な対話の初期候補は方針書の18問です。自動選択はこの入口集合に限り、本人がtopicを選ぶか適用候補集合が与えられた時に対象を広げます。18問すべてに答える要件はなく、既知goalと非回答を除外します。候補順は入口の順序、P0/P1/P2、IDの順に決定します。優先度は個人の価値を数値化するものではありません。

## 検証と残る限界

`node --test tests/planner.test.mjs` は300問の構造と対応、18候補、拒否のカテゴリ越しの継承、goalごとの共通予算、明示の再開、既知goal・不明・保留の除外、目的フィルタ、純粋性を検査します。最初は実装モジュールが存在しないことによる失敗を確認してから実装しました。全goalの別IDに対しても拒否と予算上限を検査します。

これは300問の内容妥当性、言い換え全体の意味的一致、個別利用者への有用性、長期面談の負担を実証するテストではありません。原案の適用条件は自然言語であり、purposesだけで「今この質問が必要」を完全には判断できません。必要に応じて呼出側で `applicableIds` を絞り、不足が判断を変えなければ質問を止める必要があります。原案のAC01・AC22・AC47には別途、意味と実利用の評価が必要です。面談状態から本人確認、保存・送信・実行の権限は生じません。
