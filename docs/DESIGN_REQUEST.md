# 個人コンテキストOSSの設計レビュー依頼

対象リポジトリ： https://github.com/rasokiwayami/aun

このリポジトリの現状コードを読んだうえで、汎用の個人コンテキストOSSを再設計してください。実装を追認するのではなく、目的に合わない前提や構造があれば具体的な置き換えを提案してください。今回は設計・質問作成・評価計画を依頼します。リポジトリへの書き込み、個人情報の追加取得、外部サービスへの設定変更は求めていません。

まず `README.md`、`docs/CURRENT_STATE.md`、`SECURITY.md`、`src/conversation.mjs`、`src/interview-policy.md`、`src/questions.json`、関連テストを読んでください。参照できたコミットとファイルを明記してください。GitHubを取得できなかった場合は、その事実と必要なファイルを挙げ、読めた体で設計しないでください。

## 製品の目的

利用者が自然な会話や任意の資料から、自分の価値観・思想・好み・判断条件・制約・例外・現在の状態を整理し、本人が確かめて直せる形で保有する。その情報を普段のAI利用に必要な分だけ渡し、毎回の説明し直しと、本人の意図に合わない提案・文章の修正を減らしたい。

質問への回答数を増やすことや、固定の性格プロフィールを完成させること自体は目的ではありません。多くの個人情報を安全に扱える拡張性を持ちつつ、必要性のない収集は避けたいです。利用者自身が情報を持ち出せること、何が使われたか分かること、誤解を直せることを重視します。

## 依頼する設計

### 1. 汎用の質問集を新しく作る

現在の200問は参考資料です。特定個人・職業・年齢・文化・家族構成を前提にせず、改めて全体を設計してください。300問程度、必要ならそれ以上になって構いません。数合わせや似た質問の水増しは避け、優先度を付けてください。

最優先は、誤解すると支援の質や本人の負担に大きく影響する質問です。自由・目的・思想・価値の衝突、研究と学習、仕事と生活、対人関係、創作・娯楽、美意識、意思決定、不確実性、AIへの委任、情報の共有、変化と訂正などを広く検討してください。機微情報の詳細ほど優先度が高いという設計にはしないでください。

各問に安定ID、カテゴリ、優先度と理由、何の判断に役立つか、基本の聞き方、適用条件、必要な場合の追質問、十分聞けたとする条件、感度と答えない選択、更新契機を付けてください。AI内部の設計情報を、そのまま利用者の画面へ大量表示しないでください。

最初の10〜20問と、その後の適応的な順序を具体化してください。全員に全問を聞かず、一度の発言で複数の問いが満たされた場合、分からない場合、拒否した場合、疲れた場合、自由に話した場合を扱ってください。誘導・診断・迎合・同じ内容の再質問を避ける例も示してください。

### 2. 回答を正確に保存する

音声からの誤変換、途中の断片、発言の訂正、話題の変更、話者の取り違え、通信切断、重複送信、同時編集、クラッシュを考慮してください。原文と修正後の文字起こし、モデルの解釈、本人確認の履歴を混同しないスキーマと状態遷移を設計してください。音声保存の有無は別の選択にしてください。

発言の日時と、内容が指す時期と、本人が確認した日時を区別してください。削除・訂正できる権利と、出典や更新履歴を保つ必要をどう両立するかも説明してください。単に追記専用にして削除不能にしないでください。

### 3. 抽象化と訂正を設計する

個別の回答を、状況・目的・適用範囲・例外付きの再利用可能な知識へ変換する方法を提案してください。事実、好み、価値観、方針、現在状態、AIの仮説、外部行為の権限を分けてください。

原文 → 整理案 → 本人の確認 → 用途別利用の各段階を追えること。推測の正確さを固定の信頼度だけで保証しないこと。一度の修正を恒久的な好みと決めつけないこと。矛盾が時期や状況の違いなら両立させること。訂正・撤回・削除が、要約、検索索引、キャッシュ、出力済みファイルなどへどう伝わるかを具体化してください。

毎回の確認作業が重くならないよう、まとめて確認、差分だけ確認、未確認のまま保留する仕組みを設計してください。

### 4. 普段から活かせる仕組みを作る

相談、比較、学習、文章作成、予定や依頼の判断などで、今の目的に合う情報だけを取り出す流れを示してください。全文投入、全文検索、構造化ルール、検索拡張などを比較し、必要性と費用から選んでください。

内部の判断に使ってよい情報と、相手に見せる文章へ出してよい情報を分けてください。Markdown/JSON等の持ち出し、プロンプトへの添付、将来のAPIやMCPなどを段階分けし、特定AIへの囲い込みを避けてください。対応していないChatGPTのメモリやGPTs設定への書き込みが可能だと仮定しないでください。

情報がない・古い・矛盾する・参照できない場合に、勝手な補完や同じ質問の繰り返しを避ける動きを示してください。

### 5. 大量の個人情報を扱う安全性とOSS運用

収集の必要性、目的別同意、感度、第三者情報、端末外への送信、暗号化、鍵、保持期間、削除、復元、端末紛失、エクスポート、プラグイン、ログ、依存関係、プロンプトインジェクションを実際のデータの流れに沿って検討してください。ローカル動作だけで安全とはせず、現状コードの脅威と限界を指摘してください。

本人の発言や参照文書を実行権限にしない境界を設計してください。認証、モデル、音声、保存の交換可能な範囲を検討し、今の非商用認証DevKitの条件も踏まえて、OSS本体と任意の連携を分けてください。過剰な抽象化や大規模な基盤を最初から必須にしないでください。

### 6. 役に立ったことを測る

同じ課題について、コンテキストなし・現状方式・提案方式を比較する評価を設計してください。説明し直しの回数、修正の回数と大きさ、誤った一般化、古い情報の適用、不要な個人情報の開示、本人の確認負担、返答までの時間、費用を含めてください。

合成データで確かめられることと、本人の許可を得た実利用でしか分からないことを区別してください。質問の内容妥当性、抽象化の根拠、訂正の伝播、削除、利用時の検索・適用までつながる受入テストを提案してください。

## 欲しい成果物

1. 現状コードの問題点：重要度、該当ファイル・関数、具体的な失敗場面、根拠、修正案。
2. 全体設計：データの流れ、責務、スキーマ例、状態遷移、確認・訂正・削除・共有の動線。
3. 優先度付き汎用質問集：300問を目安に、最初に聞く質問と条件付き質問を区別。
4. 具体的な利用例：会話から保存・抽象化・本人確認・日常での適用・訂正までを複数の架空人物で示す。
5. 評価計画と、最初に成立させる小さな製品範囲。その後の段階的な実装順と既存コードの扱い。

長くなる場合は、最初に設計上の重要な判断と全体目次を出し、質問集などを省略せず、複数の成果物に分けてください。事実・推論・提案・未確認を分け、実現不能な完全性や安全性を約束しないでください。
